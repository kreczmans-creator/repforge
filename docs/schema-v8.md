**Report contract (R-04 to R-07, Review A M1).**
- Category codes (R-05, final, persistent internal identifiers; display labels are decided separately): `migrated` (migrated successfully), `preserved` (preserved unchanged), `quarantinedOrUnresolved` (quarantined or unresolved), `rejectedOrBlocked` (rejected or blocked), `warningForReview` (warnings requiring review).
- Reconciliation (R-04): per run and table, the four exclusive outcomes `migrated + preserved + quarantinedOrUnresolved + rejectedOrBlocked = examined`; every examined record belongs to exactly one. `warningForReview` is an additional count, may reference records in any outcome and never enters the sum.
- Counts by disposition (Review A M1): D04 "Report detail" also asks the report to state records blocked, quarantined and rejected. `migration_report_counts` therefore holds a second dimension, `disposition`, with one count per action; each equals the number of entries of that run and table with that disposition. This implements both owner statements together (the approved categories and the stated counts); it is not a new rule. Cross-row sums cannot be a CHECK; the 3b-4 writer and its tests enforce them (a test shows both queries over stored rows).
- Value encoding (R-06): `original_value` and `resulting_value` are JSON text, NOT NULL, `json_valid`: SQL NULL → `null`; TEXT → JSON string (the text `null` → `"null"`, the empty text → `""`); INTEGER and REAL → JSON number; BLOB → `{"blob":"<base64>"}`. `original_value` always holds the **whole** stored field value, also for an element entry (`position` set): for example the raw `secondary_muscles_json` text `["chest",null]` is stored as the JSON string `"[\"chest\",null]"`, and the offending element is in `element` as compact JSON (`null`). A SQL NULL field (`original_value` `null`, `element` NULL) and a JSON null element (`element` `null`) therefore never share a column. This matches the WS4 contract (`app/lib/domain/library/migration_report.dart`, `encodeStoredValue`). SQL NULL, JSON null text, strings and numbers stay distinct; nothing collapses into an empty string. `resulting_value` is `null` where nothing is used operationally.
- Event ids (R-07): deterministic from run id, table, record id, field, position and rule (3b-4 fixes the exact concatenation and hash). A resumed migration reuses its run id, so it rewrites no entry twice; a genuinely new attempt gets a new run id.
- WS4 report contract (WS4 review, L8): `element` holds the compact JSON of the offending array element (for example one entry of `equipment_json`), NULL otherwise; `block_reason` is set exactly when `disposition` is `blocked` and takes the `exercise_blocks` reasons (`noPrimaryTarget`, `unknownEquipment`, `invalidEquipment`, and since the decision baseline `invalidSecondaryTarget`, `invalidClassification`, `invalidAliases`). Both lists are extended together. Every block row has exactly one `blocked` entry of the run that wrote it.
- Provenance (R-08): `provenance_kind` (`device` for a run produced on this device, `backup` for one merged in from a restored backup), `provenance_source`, NOT NULL (for `device` a stable install or source label; for `backup` the backup identity, such as the file name or the content hash), `app_version`, NOT NULL, `merged_at` (exactly for merged runs). `id`, `generated_at` and `app_version` stay as recorded where the run was produced.

**Release record (R-10, R-30 option b).** 3b-4 records release 1 from the SHA-256 of the exact bundled seed-file bytes, lowercase hex; the row states `sha256` and `hex-lower`. Nothing hashes a re-serialised form. Release 1 is recorded **only** when those bytes hash to the pinned v7-era value `839d9ca28f043e61ed502b4bf765ca1ff8110fc21b54e84d98014c3b8d5e0b22` (`V7ToV8Migration.v7SeedSha256`; the hash of `app/assets/seed/exercise_library.json` at df326db, its only commit); counts NULL; `applied_at_source` = `seedExercisesVersion.updated_at`. Anything else is reported (rule `R-30`) and creates no row (section 7).

**Bootstrap** (`onCreate`, later the migration): provider `repforge` with the licence-register template values, `attribution` NULL until stage 3c (R-09); 31 anatomy nodes (19 preserved ids and 12 ancestors) with parent, level, flag and sort of `anatomy.json`; the 21 existing equipment items with sort and default role of `equipment.json`. Statements `INSERT … ON CONFLICT (id) DO NOTHING` (exposed as constants and tested): an existing device row wins silently (R-23); a CHECK, NOT NULL or foreign-key violation still fails (tested with injected rows).

**Domain change and the IC-315 text (Review A, L6).** IC-315 now also refuses a role override on an item whose default role is `cardio` or `implement`, for every source (owner decision Q6, ADR-0008 section E: "The domain check and a test enforce it"). The approved `quality-and-duplicates.md` IC-315 text names only "an item not in the exercise equipment list, a role other than `load` or `support`, or has no note". It is not edited here: ADR-0008 E Q6 (approved later) extends the rule, and this divergence is recorded here and in the WP 8 record for the owner's next update of the approved document.

## 6. The v7 → v8 migration (sub-stage 3b-4; Review B conditionally sound, fixes applied, awaiting re-check)
Code: `app/lib/data/db/migration/v7_to_v8.dart`, run by `RepforgeMigration` from `AppDatabaseV8` (section 1). Not connected to the app: only isolated tests and fixtures reach it; production stays at schema 7.

**Order inside the single v7 → v8 transaction** (foreign keys off before it and verified off; `PRAGMA user_version = 8` its last statement):
1. guard: `exercises` already without `primary_muscle` and a recorded 7 → 8 run → nothing is written (repeated run); without the run row → `V8MigrationFailure(unexpectedState)`; a v7 database that already holds any v8-only table or index → `V8MigrationFailure(unexpectedState)` (Review B, L6);
2. run id from the ledger (R-32, below), before the first write;
3. baseline: whole-database `PRAGMA foreign_key_check` and the unresolved exercise references IC-901 to IC-903 (`session_sets`, `session_exercises`, `plan_exercises`, `exercise_user_state`, `exercises.copied_from_id`), keyed by table, primary key, column, parent and rule (never by rowid, which a rebuild may change);
4. every missing v8 table and index of `Schema8`; the run rows; the bootstrap (device wins, R-23);
5. every exercise through `mapLegacyExercise`: quarantine rows (originals of incomplete conversions only, ADR-0008 E clarification 3), then `exercises` rebuilt by `TableMigration` with `source`, `provider_id` and `revision` taken from the mapping through a temporary table (WS4 is the only source of truth), then targets (contiguous ordinals checked, R-11), equipment links and one block per reason (R-01, R-02);
6. every set through `classifyLegacyExertion`: original pair quarantined, both columns cleared (R-28), then `session_sets` rebuilt with the TRN-020 CHECK;
7. release 1 (R-30 option b, section 7); the pre-v8 quarantine rows into the report as retained (R-33);
8. broader review: whole-database findings after the work; any finding not in the baseline aborts; baseline findings that remain go to the integrity run;
9. report entries and counts of both runs;
10. targeted check (`foreign_key_check` per table on `exercises`, `session_sets`, `session_exercises`, `plan_exercises`, the exercise children, the reference tables, `catalogue_releases` and the report tables, plus the references above) against the baseline: anything new aborts;
11. self-checks: `reconcileReport` of both runs with the independent input counts and `affectedByTable` from the mapping's own block and quarantine lists (WS4 N2); every `quarantined` entry of the run has a quarantine row of the run (since every quarantined exercise value now also blocks, this catches a dropped quarantine list); row counts of `exercises` and `session_sets` unchanged; stored provenance equals the mapping; the stored entries (every column) and counts of both runs equal the built report (Review B, L5). Any failure → `V8MigrationFailure(selfCheckFailed)`, rollback.

**Preflight.** `RepforgeMigration.preflight` runs before the keys are switched off and before any step (so a v3 database is not touched either): `PRAGMA quick_check` (or an injected result, only through the test-only `V8MigrationConfig.forTesting`, Review B L10) through `evaluateIntegrityPreflight`. On anything but one `ok` row it throws `IntegrityPreflightFailure` with the WS4 outcome (verbatim diagnostics, user message, `writesAllowed` false); nothing is written, the ledger included. `findIntegrityPreflightFailure` and `unwrapRemoteError` remove `DriftRemoteException` layers (background-isolate connections).

**Contract details fixed by 3b-4** (within the decided contracts; Review B to confirm):
- Event id (R-07): WS4 `migrationEventId`, SHA-256 lowercase hex of `["repforge.migrationEvent/1", runId, table, recordId, field, position, rule]` as compact JSON.
- Run ids: a new id from `V8MigrationConfig.newRunId` (production: a UUID); the integrity run is `<run id>:integrity`. All migration timestamps (`generated_at`, `quarantined_at`, `blocked_at`) are the run's `generated_at`, so a resumed run writes exactly what an uninterrupted one would.
- Provenance (R-08): `provenance_kind` `device`, `provenance_source` = `V8MigrationConfig.installLabel`, `app_version` = `V8MigrationConfig.appVersion`.
- Counts: both dimensions are written for every examined table with every code, zeros included (6 category rows, 9 disposition rows). The `warningForReview` category row counts **records** with at least one warning entry (`record_count`), never added to the outcomes.
- `resulting_value`: a WS4 event without a resulting value is stored as JSON `null` (column NOT NULL).
- `quarantine_id`: set on every entry whose table, record and field have a quarantine row of this run (or, for a pre-v8 quarantine entry, that row).
- `exercise_id`: the exercise itself for `exercises`; the set's `exercise_id` for `session_sets`; `row_id` of a pre-v8 quarantine row from `exercises`; for an integrity finding, the record's `exercise_id` column (the exercise itself for `exercises`).
- `exercise_blocks.original_json` (R-06 encoding): `noPrimaryTarget` and `invalidSecondaryTarget` → `{"primary_muscle":…,"secondary_muscles_json":…}` (the original target state); `unknownEquipment`, `invalidEquipment` → `{"equipment_json":…}`; `invalidClassification` → `{"type":…,"category":…}`; `invalidAliases` → `{"aliases_json":…}`.
- Quarantine order: exercises by id (each mapping's requests in order), then sets by id.
