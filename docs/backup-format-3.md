## 2. Format 3

```json
{
  "app": "repforge",
  "formatVersion": 3,
  "schemaVersion": 8,
  "appVersion": "<the exporting app's version>",
  "exportedAt": "<UTC ISO-8601>",
  "releaseLog": [
    {"providerId": "repforge", "release": 1, "contentHashAlgorithm": "sha256",
     "contentHashEncoding": "hex-lower", "contentHash": "<64 hex>"}
  ],
  "tables": { "<every v8 table>": [ { "<column>": <value>, ... }, ... ] }
}
```

- **Every** v8 table is present (38, in `AppDatabaseV8` order), user, exercise, reference, catalogue and report tables alike: `exercise_targets`, `exercise_patterns`, `exercise_equipment` (with `role_override` and `override_note`), `exercise_names`, `exercise_user_state`, `exercise_blocks`, `content_providers`, `catalogue_releases`, `anatomy_nodes`, `movement_patterns`, `equipment_items`, `reference_labels`, `migration_runs`, `migration_report_counts`, `migration_report_entries`, `legacy_quarantine` and all user tables. Rows are the raw stored values (`SELECT *`, rowid order), so stable ids and every relationship travel unchanged. `sqlite_sequence` is not exported.
- Values: SQL NULL → `null`, TEXT → string, INTEGER → integer, REAL → number (Dart writes a fraction or exponent). Report values keep the R-06 JSON-text encoding inside their TEXT columns.
- `releaseLog` is the release identity of every `catalogue_releases` row (provider, release, algorithm, encoding, hash). It is the same fact as the table; restore rejects a file whose log and table differ.
- A v7 app refuses the file ("made by a newer version", `parseBackupEnvelope` with supported format 2) and changes nothing (tested).

## 3. What a restore does with each table

| Class | Tables | Restore |
|---|---|---|
| User data | measurements, foods, food_servings, food_log_entries, saved_meals, saved_meal_items, recipes, recipe_ingredients, recipe_substitutes, meal_plan_items, prep_batches, workout_plans, plan_exercises, workout_sessions, session_exercises, session_sets, scheduled_workouts, training_splits, split_days, goals, settings, exercise_user_state | All rows deleted, the backup's rows inserted (OQ-17 replace; v7 contract). `legacy_quarantine` is merged history (next row) |
| Exercise aggregate | exercises and its owned rows (targets, patterns, equipment, names, blocks) | `user` and `imported` exercises on the device are user data: replaced with the backup's. A `system` exercise on the device is catalogue content and is never deleted. **Field-level ownership (B-01, decided):** its catalogue fields (every column except `archived` and `deleted_at`, including `source`, `provider_id` and `revision`) and its owned rows stay the device's (Q15), each difference reported; its user fields `archived` (R-24) and `deleted_at` take the backup's value. A different system/user classification or provider never rejects the restore by itself. A system exercise only in the backup is inserted |
| Reference and catalogue | content_providers, anatomy_nodes, movement_patterns, equipment_items, reference_labels, catalogue_releases | Never deleted. Missing rows inserted; an existing device row is never overwritten; a different **immutable** value (register B-04; `equipment_items.default_role` decided by Q8/R-20) rejects the whole restore; a different mutable value keeps the device value and is reported (`retained`, `warningForReview`). Formats 1 and 2 hold no reference rows: the migration's bootstrap rows are inserted where missing (R-23, device wins) |
| Report history | migration_runs, migration_report_counts, migration_report_entries | Merged, never replaced (section 6) |
| Quarantined originals | legacy_quarantine | **Merged (B-03, decided):** the device's rows are kept; a backup row with the same content (source table, record, reason, original, time) is the device's row and is not written again; a backup row whose id is free keeps it; a backup row whose id is taken by another device row gets a new id and the merged entries' `quarantine_id` follow it. A format 3 entry whose link has no row in the backup is refused (phase 1a). Never counts as user data for "empty" (B-08) |

## 4. Order of work

**Phase 1a — pure** (`planRestore`; also the whole of `previewJson`, which the port requires to be synchronous):
1. `parseBackupEnvelope` (supported format 3): not JSON, not RepForge, newer format, no tables → rejected. Format < 1 → "unknown format". Format and schema must pair: 1 with schema 1–7, 2 with 7, 3 with exactly 8 (a missing `schemaVersion` is accepted for formats 1 and 2, as production did). Format 3 needs `appVersion`.
2. Tables: format 3 needs exactly the v8 table set; formats 1/2 accept only v7 table names. A table that is not a list, a row that is not an object → rejected (B-09).
3. Formats 1 and 2, per row, the v7 restore contract and then the migration's rules:
   - recipes with `method_steps_json` (schema ≤ 4): production's v4 mapping (copied);
   - exercises with `is_custom` (≤ 5), plan exercises with `target_reps` (≤ 5), sets without `energy_kcal` (≤ 5): the frozen v6 mapping (`LegacyTrainingRowsV6`), its quarantine row recorded exactly as production restore records it (original row as JSON);
   - every exercise: v7 columns, types and NOT NULL checked, `supplied` 0/1 (v7 CHECK), then `mapLegacyExercise` → v8 row (`source`, `provider_id`, `revision`), targets (contiguous ordinals), equipment links, one block per reason (R-01, R-02), quarantine requests and report events;
   - every set: `classifyLegacyExertion` (TRN-020): an invalid pair is quarantined, both columns cleared and reported (`cleared`, rule TRN-020); it is never rejected by the CHECK;
   - a backup without `session_exercises` is marked for the frozen v6 → v7 backfill.
4. Every resulting row against the mirror: unknown column, type (strict), NOT NULL (defaults applied), every CHECK; primary keys and UNIQUE sets per table; every foreign key whose parent the backup itself must hold (user parents, exercises, report runs).
5. Format 3 report history: each entry through the WS4 `ReportEvent` constructor (R-06 canonical encoding, action-category rules, block reason) and its stored event id re-derived (R-07); per run and table: the four outcomes sum to `examined`, every disposition count equals its entries, the warning count equals the records with a warning entry; entries without counts rejected. Every `quarantine_id` of an entry must have its `legacy_quarantine` row in the backup (B-03).
6. Structurally empty → "This backup contains no records. Nothing was changed." (B-08): format 3 counts the rows of the user tables (not `legacy_quarantine`, merged history since B-03) and the `user` and `imported` exercises only (owner decision; a catalogue-only file can never wipe user data) (system exercises are catalogue content the device keeps; reference and report rows restore nothing of the user's); formats 1 and 2 keep the v7 rule.
7. Envelope keys allow-listed (review O1): formats 1 and 2 `app`, `formatVersion`, `schemaVersion`, `exportedAt`, `tables`; format 3 adds `appVersion` and `releaseLog`; anything else rejects.
8. Exertion columns of formats 1 and 2 (review M1): a JSON boolean, array or object in `exertion_scale` or `exertion_value` is refused before the TRN-020 classification (a text or a number is classified, and a text value is quarantined and cleared as `valueNotNumber`). Anything unexpected while reading a file becomes a `RestoreRejected`, so `previewJson` never throws.

**Phase 1b — reads the device, writes nothing** (inside `importJson`, **inside the write transaction**, after foreign keys are switched off and before the first write, so nothing can change between the checks and the writes; a rejection rolls back a transaction that has written nothing; review L3): reference conflicts and missing rows; system exercises (immutable conflict, device wins, differences); IC-315 on every equipment link to be written, with the item's default role resolved from the device, the backup's new rows or the bootstrap (R-19); every foreign key of the **composed** state (device rows kept + rows to insert); for format 3, the domain rules on every exercise the restore inserts (`restoreDomainProblems`, register B-15; review H1), including the unreadable-data rule: an unreadable type, category or aliases restores only while blocked for it; for formats 1 and 2, a system exercise the restore would insert without a valid primary target (owner decision on H1); the quarantine merge (B-03); the report merge (runs, entries, counts: conflict, present, missing); the new run id not yet recorded. Any finding → one `ValidationError` listing the details, nothing changed.

**Phase 2 — the same transaction** (`PRAGMA foreign_keys = OFF` before it, outside any transaction, verified 0, and 0 at every checkpoint (tested); restored to the previous value after commit or rollback and verified):
1. baseline: whole-database `foreign_key_check`, keyed by table, primary key, parent and key id; row counts;
2. delete the user tables except `legacy_quarantine` (B-03); delete user/imported exercises and the owned rows of every non-system exercise (keys are off: nothing cascades; the deletes are explicit);
3. reference rows: the bootstrap where missing (formats 1/2), the backup's missing rows (format 3);
3a. the user fields of device-kept system exercises from the backup (B-01);
4. exercises to insert with their rows (blocks of formats 1/2 stamped with the restore time);
5. user rows; `legacy_quarantine` merged (B-03: matched rows skipped, free ids kept, colliding ids renumbered), then the new rows (v6 mapping, then v8 mapping: exercises by id, then sets by id, as the migration orders them) with autoincrement ids, stamped with the restore time; quarantine rows of a system exercise kept from the device are not written; Then, for formats 1 and 2, release 1 (B-07, the migration's rule): when the restored `seedExercisesVersion` parses to 1 or more and the device records no release 1 of `repforge`, the row is written only when the bundled seed (`BackupV8Config.loadSeedBytes`) hashes to the pinned v7-era value `V7ToV8Migration.v7SeedSha256`, with `applied_at` = the setting's `updated_at`, `applied_at_source` = `seedExercisesVersion.updated_at` and NULL counts and `app_version`; any other hash or unreadable bytes → no record and the migration's R-30 warning on the setting. A device that already records release 1 keeps its record (B-04).
6. the frozen backfill (pre-v7 backups);
7. report merge (section 6); the restore run and, when there is a finding, its integrity run;
8. `foreign_key_check` again: any violation not in the baseline aborts (safeguard A);
9. self-checks: every table holds exactly the composed number of rows; the restore report reconciles (`reconcileReport` with independent examined counts). Any failure → rollback, `StorageError('Restore failed; nothing was changed.')`.

## 5. Formats 1 and 2: the same result as the migration

For every clean frozen golden, the v8 restore gives **exactly** the database that production `importJson` (v7) followed by the 3b-4 migration gives: every user, exercise and reference table row for row and typed, the column lists, and the restore run's entries and counts equal the migration run's (apart from run-derived ids). Differences by design: the run ids and provenance (a restore run, not a migration run), and release 1 (register B-07). On a device that already holds system exercises (a migrated device), those stay the device's rows (B-01); a v7 backup of the same data reports no difference.

## 6. Report history

- **The restore run** (R-08): new run id per restore from `BackupV8Config.newRunId` (production: a UUID; refused before any write if already recorded). It never reads or writes the migration run ledger (R-32), and an in-memory database is no different (Review B N2). Row: `trigger_kind` `restore`, `from_version` = the backup's schema version (NULL when a format 1 file omits it), `to_version` 8, `generated_at` = `merged_at` = restore time, `app_version` = this app, `provenance_kind` `backup`, `provenance_source` = `sha256:<hex>` of the exact backup text bytes (B-10).
- **Its entries**: formats 1/2 — the mapping events of every inserted exercise (`migrated` clean outcome), every set's TRN-020 events (`preserved` clean outcome), and every pre-v8 quarantine row (the backup's and the v6 mapping's) as the migration lists them (R-33). All formats — a `retained` / `warningForReview` entry, rule `D04-RESTORE-DEVICE-WINS` (B-06), per difference between a backup value and the device value that wins (reference rows and system exercises: one entry per column, or per owned table as canonical JSON). Counts: both dimensions for every examined table, zeros included, as the migration writes them; `quarantine_id` and `exercise_id` filled as the migration fills them.
- **Integrity run** (`<run id>:integrity`, `integrityCheck`, provenance `device` with the install label): unresolved exercise references after the restore (IC-901 sets and session entries, IC-902 plan entries and user state, IC-903 `copied_from_id`), action `none`, never blocking, never repaired — R-31 applied to a restore, written only when there is a finding (B-11).
- **Merge of a format 3 backup's history** (D04 "Restore conflicts", R-07, R-08):
  - run: absent → inserted; a run produced on its device (`device`) becomes `backup` with this backup's identity and the merge time; a run already merged elsewhere keeps its provenance; present with the same produced fields (`trigger_kind`, versions, `generated_at`, `app_version`) → kept as on the device (its provenance and merge time stay the first ones); different → **reject** (B-02);
  - entry by `event_id`: absent → inserted unchanged; present and identical (every column except `acknowledged_at`) → skipped; different → **reject** (B-02); `acknowledged_at` stays the device's (B-05);
  - count by (run, table, dimension, code): absent → inserted; same → skipped; different → **reject**.
  - Repeating the restore of the same backup inserts nothing from the backup a second time (tested three times in a row); each restore adds only its own run.

## 7. Errors

All phase 1 findings are `ValidationError(field: 'file')` with the reason and the affected records (first 20, then "and N more"), ending "Nothing was changed.". Phase 2 failures are `StorageError('Restore failed; nothing was changed.', cause)`. Examples: "This backup conflicts with the data on this device: equipment_items barbell: default_role is "support" in the backup and "load" on this device (a default role never changes: ADR-0008 E Q8, R-20). Nothing was changed."; "… exercise_equipment ex-rich/treadmill: an item with the default role cardio takes no role override (IC-315, ADR-0008 E Q6)".

**O6, repeated restores and `legacy_quarantine`.** A backup's own quarantine rows are matched (B-03, O5), so repeating a format 3 restore adds no quarantine row. Repeating a **format 1 or 2** restore does add rows: the v6 and v8 mappings run again and each restore writes its own quarantine rows for the values it cleared or quarantined, linked from its own restore run's entries (distinct runs, distinct event ids). The table therefore grows by the same number of rows with every repeat of the same v7 backup; nothing is lost or duplicated within one run. Accepted as the record of each restore; noted for the 3d report screen.
