## S3 implementation notes (Fuel: G3, G4)
- G3a: the food-search screen has a "Pick from library" row (`search-pick-recipe`, `search-pick-saved-meal`). It opens the existing `RecipeListScreen` / `SavedMealsScreen` with `?pick=1` (`RfRoutes.fuelPickRecipe`, `fuelPickSavedMeal`). A recipe tap opens the existing recipe log sheet; the saved-meal screen's existing "Log this meal" action logs it. Both log to the selected day, then the add flow pops back to Fuel. No second list, no new tab, no change to `LogRecipe`/`LogFood`.
- G3b (NUT-014): `FoodLogRepository.recentSources` (read-only SQL over `food_log_entries`, grouped per source, newest first) and use case `LoadRecentItems` (returns `Result`, resolves to live foods/recipes, skips deleted ones, limit 10). Shown as `search-recent` while the query is empty. Saved meals are not in the recents list (they have no id on the log entries).
- G4a: `recipe-duplicate` on the recipe detail app bar calls `SaveRecipe(saveAsNew: true)` with name suffixed " (copy)" and favourite false, then opens the copy.
- G4b: `recipe-category-filter` chip row built from distinct stored categories; combines with search and favourites; in-memory only.
- Meal slot: the sheets keep their existing time-of-day default and meal selector; there is no separately selected meal on Fuel.

## S4 implementation notes (Train, G5 and G6)
- G5a/b/c: `DuplicatePlan`, `DeletePlan`, `SaveSessionAsPlan` in `features/training/application/plan_actions.dart`; actions `plan-duplicate-<id>`, `plan-delete-<id>` (confirm `plan-delete-confirm`) on the plan list and `detail-save-as-plan` on the session detail (opens the new plan in the editor). Save-as-plan carries no loads; targetSets is capped at 20 (plan validation limit); the most common recorded rest wins, earliest on a tie. Plan delete is a soft delete of the definition only; a split day that lists a deleted plan keeps its reference (not changed here).
- G6a: `session-elapsed` on the session screen, ticking from the injected clock every second while unfinished, fixed at `endedAt` once finished.
- G6b: the session body is now a `ReorderableListView` (header and footer carry the rest of the page); drag handle `entry-drag-<entryId>` with semantics label "Drag to reorder <name>"; the up/down buttons remain.
- G6c: **deferred to v9.** `SettingsRepository` exposes only typed accessors; storing a running timer's end instant and session id needs a new method on the domain interface and its Drift implementation (plus fakes) under `lib/data/**` and `lib/domain/settings`, which this stage may not touch, and restoring it also needs controller changes. Not clean without those, so the rest timer remains in memory only (background alert via notification unchanged).
