## Date and time semantics (assumptions, recorded)
- `recordedAt` is an instant stored as UTC; ranges, "today", "future" and comparison dates use the **local calendar date** of that instant. `dayStartHour` (diary day, OQ-18 open) is **not** applied to measurements: a measurement belongs to the calendar date it was taken. Tests pin a non-UTC time zone.
- An entry taken "today" defaults to the current time; a back-dated entry defaults to 12:00 local on the chosen date (editable).

## Decisions requested at stage 0 (history; decided above)
- **D1 — BCM-006 smoothing (D04 labels the method a proposal).** Ambiguities in "7-day moving average over days with entries": per-entry or per-day mean; window of 7 calendar days or of the last 7 days that have entries; trailing or centred. **Recommendation:** trailing window of 7 calendar days ending on each day that has an entry; first average each day's entries, then average those daily means; draw a trend value only when the window holds at least 3 days with entries (D04 "fewer than 3 entries" read as days with entries); raw entries always drawn. Implemented as one pure function so another choice changes one place. **Decided 2026-11-05: approved, with the threshold corrected to at least three individual readings in the window (not three distinct days); no "proposed" label.**
- **D2 — file output for CSV and backup (new platform capability).** The app has no way to hand a file to the user. **Recommendation:** ADR-0011 (proposed, `docs/adr/ADR-0011-file-export-and-import.md`; `share_plus` 13.3.1, `file_selector` 1.1.0): `share_plus` (system share sheet: save to Files/Drive, email) for exports and `file_selector` for choosing a backup to restore, both behind a Flutter-free port in `lib/data/platform/` with a fake for tests (ADR-0006 standing constraint), pinned to releases at least two weeks old. Stage 3 waits for this decision; stages 1–2 do not depend on it.
- **D3 — backup export/import screen.** D06 WP 10 scope and the WP 3 record allocate the export/import screen to WP 10; the owner's instruction says to reuse the existing mechanism. **Proposed:** a minimal screen in Settings using the existing `DriftBackupRepository` only — export file; restore showing record counts and backup date with confirmation; invalid or newer files rejected without change (DAT-004(1)(2)). DAT-005(2) (published schema) and DAT-006 for other domains stay out of scope. Confirm or remove from WP 10.
- **D4 — "compare two periods".** **Proposed:** for dates, the reading on (or nearest to) each date; for periods, the mean of the readings in each period with the count shown. **Approved 2026-11-05**; a date without an exact reading returns both nearest neighbours and the user must choose (no silent substitution).
- **D5 — CSV columns.** **Proposed:** `date` (ISO 8601 local date-time with UTC offset), `type` (site name, e.g. "Left thigh"), `value`, `unit` (kg or cm); UTF-8 with header row; one row per reading. **Approved 2026-11-05.**

### Stage 1 details
- **Strict input (BCM-001(1), BCM-002(1)).** `Kilograms.of`, `Centimetres.of` and the new `Centimetres.parse` reject out-of-range and off-step values (0.1 steps, 1e-9 tolerance for float noise); nothing is rounded (80.05, 80.15, 19.9, 500.1 rejected; 80.1 accepted). Stored readers `fromStored` (throws when invalid) and `tryFromStored` apply the same strict rule (range, 0.1 step, 1e-9 float noise only) and never snap; they are for `lib/data` only; `test/architecture/cardio_energy_isolation_test.dart` now also guards them. Behaviour change for existing callers: `RecordBodyWeight` / `Kilograms.parse` now reject `82.45` instead of storing 82.4 (the weight screen shows the validation message); the measurement mapper reads with `tryFromStored`. No other user of `Kilograms`/`Centimetres` exists (goals, dashboard and nutrition targets only display `WeightEntry.weight`).
- **Site help.** `MeasurementSite.helpText` (original text; waist at the navel; limb sites carry "Measure the same side consistently"), plus `counterpart`/`isBilateral` for pairing left and right.
- **Use cases** (`lib/features/measurements/application/`, Result/AppError, `catch Object` becomes `StorageError`): `RecordMeasurementEntry` takes `Map<site, text>`; blank text means not measured (no row, never 0); at least one value; every value strictly validated before anything is written; one row per provided site, same `recordedAt`, inserted atomically (`MeasurementRepository.insertAll`, a transaction); the note applies to every row of the entry. `UpdateMeasurement` replaces value, `recordedAt` and note of one row (site fixed; other rows untouched; `NotFoundError` if missing). `DeleteMeasurement` soft-deletes one row (`NotFoundError` if missing or already deleted). The repository gained `byId`, `insertAll`. `RecordBodyWeight`/`DeleteWeightEntry` and the dashboard are unchanged in behaviour; `RecordBodyWeight` now shares the future/note rules (`measurement_rules.dart`). Providers: `recordMeasurementEntryProvider`, `updateMeasurementProvider`, `deleteMeasurementProvider`, `measurementsForSiteProvider(site)`, `allMeasurementsProvider` (newest first).
- **Date semantics.** `recordedAt` is an instant. The repository writes UTC (`toUtc()` on insert and update, so the ISO text sort order is chronological) and returns UTC; drift reads text dates back as local `DateTime`s, normalised to UTC by the mapper. Calendar logic uses the new `CalendarDate` (`fromInstant` = local date of the instant; arithmetic on UTC dates, immune to DST). Assumption: the future check keeps the 1-minute clock-skew tolerance of WP 1 (`futureTolerance`). Tests run green under `TZ=UTC`, `Pacific/Auckland` and `America/Los_Angeles`.
- **Ranges (BCM-005).** Inclusive local dates ending today: 4 weeks = 28 dates (`today-27..today`), 12 weeks = 84 dates, 1 year = `(today - 1 year) + 1 day .. today`, all = unbounded. Assumption: a year back from 29 February rolls to 1 March.
- **D4 (approved): comparison.** Dates: `compareDates`/`pickForDate` return `ExactReading` (several readings that day: the latest), `NeedsChoice(before, after)` (latest reading of the nearest earlier date and earliest reading of the nearest later date, with their actual `recordedAt`; nothing substituted) or `NoData`. `change` is computed only when both dates are exact; after the user chooses, the UI calls `changeBetweenReadings`. The earlier date is the base whatever the argument order. Periods: `comparePeriods` gives the mean (to 0.1) and number of readings per period; the change uses the displayed means. Change: absolute and percent relative to the earlier value, each to 0.1 half away from zero; waist 90.0 to 87.5 = -2.5 cm and -2.8 % (test verbatim).
- **BCM-008 summary.** `progressSummary` returns one entry per site in enum order: `SiteProgress` (first, latest, change; at least two readings in the period) or `NotEnoughData` (with count, 0 when the site has no readings).
- **D1 (approved, with the owner's correction): weight trend.** `weightTrend`: trailing 7 calendar days ending on each day with entries; each day's readings averaged first, then the daily means averaged; a value only when the window holds at least **three individual readings** (`trendMinReadings`, not three distinct days): 3 readings on 2 days show a value, 2 readings on 2 days do not, 4 readings on one day show the daily mean. One point per day with entries (`average` null when under the threshold); raw readings untouched; gaps not interpolated. The chart label must not say "proposed" (stage 2).
- **D5 (approved): CSV.** `buildMeasurementsCsv`: header `date,type,value,unit`; one row per reading, oldest first (ties: creation time, id); date = ISO 8601 local date-time with UTC offset (`2026-11-05T14:30:00+13:00`); type = site label; value one decimal; unit kg/cm; RFC 4180 quoting, CRLF line ends; returned as text for UTF-8 encoding (no BOM). File output is stage 3 (D2).
- **JSON backup (BCM-009(2)).** Unchanged mechanism; new test round-trips measurements (incl. a soft-deleted row) through `DriftBackupRepository`.
- No schema change, no migration.
