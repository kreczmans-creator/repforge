2. **`.github/workflows/release.yml`**, triggered by tags `v*` and `workflow_dispatch` (input: an existing tag):
   - `verify`: pinned Flutter 3.47.9, `pub get --enforce-lockfile`, generated-code check, format, analyse, tests with the 80 % gate, and a check that fails unless the tag (without `v`), `app/pubspec.yaml`'s version name and a `## [X.Y.Z]` heading in `CHANGELOG.md` agree and the section is not empty. The section is passed on as the release notes.
   - `android` (needs `verify`, runs in the `release` GitHub environment so a required reviewer is the approval step, D07 2.4): the first step fails the job, naming the missing secrets, unless `ANDROID_KEYSTORE`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD` and `ANDROID_KEY_ALIAS` are all present (checked through an `env:` step because `secrets` cannot be used in `if:`; values are never printed). Otherwise it decodes the keystore to `$RUNNER_TEMP`, builds `flutter build appbundle --release` and `flutter build apk --release` with the signing values passed as Gradle properties (`ORG_GRADLE_PROJECT_RF_*`), verifies the APK with `apksigner` (and fails if the signer is the Android debug certificate, i.e. the fallback), checks the AAB with `jarsigner`, writes SHA-256 sums, uploads artefacts and creates or updates the GitHub Release for the tag with the changelog section as notes, then deletes the keystore. Missing secrets mean no release; an unsigned or debug-signed artefact is never published.
   - `ios` (macOS): simulator build only, with a log annotation that device and App Store signing are not configured; nothing iOS is attached to the release.
3. **Signing configuration** in `app/android/app/build.gradle.kts`: a `release` signing config built from `RF_KEYSTORE_PATH`, `RF_KEYSTORE_PASSWORD`, `RF_KEY_ALIAS` and `RF_KEY_PASSWORD` (Gradle properties or environment). It exists only when all four are set; otherwise the release build type keeps the debug signing, so every existing workflow and local build is unchanged.
4. **Stable certificate for test builds** in `android.yml` and `debug-release.yml`: `~/.android/debug.keystore` is restored with `actions/cache@v4` under the fixed key `repforge-debug-keystore-v1`; on a miss it is created with `keytool -genkeypair` (alias `androiddebugkey`, password `android`, `CN=Android Debug,O=Android,C=US`, 10000 days) and saved by the cache post-step. The certificate SHA-256 stays in the existing "Verify APK signatures and metadata" output (`apksigner --print-certs`). No keystore is committed (standards section 9).
   Known limits, recorded rather than hidden: (a) the first run after this change creates a keystore that differs from every earlier build, so testers uninstall once (back up data first); (b) GitHub evicts cache entries unused for 7 days or over quota, which regenerates the certificate and needs one more uninstall; (c) Actions caches are scoped to a branch and its base branch, so a keystore first created on a feature branch is not visible to `main`, and two concurrent first runs can create two keystores (the first to save wins); the certificate is therefore only stable across branches once the entry exists on the default branch; (d) the cache is not a secret store, and a debug identity with a public password is acceptable only because it signs test builds. A repository-secret keystore is the alternative and is an owner decision (see actions).
5. **NUT-023**, no schema change (see the section below).
6. **README**: a "Releases" paragraph and the test-build certificate note.

## NUT-023 — import source and date
Requirement (D04): (1) each imported food stores source name, source identifier and import date; (2) the source is visible in the food detail screen.

What is stored today (inspected, unchanged):
| Needed | Where it is stored | State |
|---|---|---|
| Source name | `foods.source`, `FoodSource` (`userCreated`, `openFoodFacts`, `seed`) | stored; Open Food Facts rows carry `openFoodFacts` |
| Source identifier | `foods.barcode`, and the food id `off:<code>` | stored for Open Food Facts: the mapper sets `barcode` to OFF's product `code` and the id to `off:<code>`. For these rows barcode and product code are the same value |
| Import date | `foods.created_at` | stored: the time the importer built the `Food` (`createdAt: now` in `open_food_facts_mapper.dart`), persisted when the food is first logged (`LogFood` upserts online foods once, never rewriting `createdAt`) |

What this stage does: `foodSourceText` / `FoodSourceLine` (`app/lib/features/nutrition/presentation/food_source_line.dart`) show one caption under the food name in the portion sheet, the screen where a food's nutrition is seen before logging: "Source: Open Food Facts · <code> · imported YYYY-MM-DD" for imported foods, "Your food · created YYYY-MM-DD" for user foods, "Source: built-in food list · added YYYY-MM-DD" for seed foods (no seed foods exist today). The date is the local calendar day of `createdAt`. NUT-023(2) is met for the portion sheet; widget tests cover imported, user-created, seed and missing-code cases.

What cannot be done without a schema change, and is left as a remaining item:
- The source identifier is the `barcode` column reused. It is a true source identifier only for Open Food Facts; a future second source, or an Open Food Facts product that should be tracked by something other than its barcode, needs a dedicated `source_id` column. There is no per-food licence or attribution text, no source URL and no source data version either.
- `created_at` is the first local storage time (the search or scan that produced the record is persisted on first log), not a separately recorded "imported at"; a food shown from a fresh search result that has not been logged yet displays the time of that search. A later refresh of the product would need its own column (`updated_at` is rewritten by edits).
- The acceptance wording "stores source name, source identifier and import date" is therefore satisfied for Open Food Facts using existing columns, and not satisfied in the general form. Whether a dedicated column is worth a schema bump is an owner decision (schema work is held with WP 8's v8/v9 sequencing; this stage touched nothing under `app/lib/data/db/**` or `app/drift_schemas/**`).
- Only the portion sheet shows the line. The diary entry edit sheet and saved-meal and recipe screens show a logged snapshot, not the food record, and were not changed. There is no food-detail screen separate from the portion sheet.
