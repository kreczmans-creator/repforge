1. **`CHANGELOG.md`** (Keep a Changelog): an `[Unreleased]` section and one entry per delivered work package (WP 0 to WP 10, WP 15, WP 17) and per campaign report, built from the delivery records. No version was invented: the app version is 0.4.0+1 and the file states that no tag has been cut.
2. **`.github/workflows/release.yml`**, triggered by tags `v*` and `workflow_dispatch` (input: an existing tag):
   - `verify`: pinned Flutter 3.47.9, `pub get --enforce-lockfile`, generated-code check, format, analyse, tests with the 80 % gate, and a check that fails unless the tag (without `v`), `app/pubspec.yaml`'s version name and a `## [X.Y.Z]` heading in `CHANGELOG.md` agree and the section is not empty. The section is passed on as the release notes.
   - `android` (needs `verify`, runs in the `release` GitHub environment so a required reviewer is the approval step, D07 2.4): the first step fails the job, naming the missing secrets, unless `ANDROID_KEYSTORE`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD` and `ANDROID_KEY_ALIAS` are all present (checked through an `env:` step because `secrets` cannot be used in `if:`; values are never printed). Otherwise it decodes the keystore to `$RUNNER_TEMP`, builds `flutter build appbundle --release` and `flutter build apk --release` with the signing values passed as Gradle properties (`ORG_GRADLE_PROJECT_RF_*`), verifies the APK with `apksigner` (and fails if the signer is the Android debug certificate, i.e. the fallback), checks the AAB with `jarsigner -verify -verbose -certs` (and fails on the same debug certificate), writes SHA-256 sums, uploads artefacts and creates or updates the GitHub Release for the tag with the changelog section as notes, then deletes the keystore. Missing secrets mean no release; an unsigned or debug-signed artefact is never published.
   - `ios` (macOS): simulator build only, with a log annotation that device and App Store signing are not configured; nothing iOS is attached to the release.
3. **Signing configuration** in `app/android/app/build.gradle.kts`: a `release` signing config built from `RF_KEYSTORE_PATH`, `RF_KEYSTORE_PASSWORD`, `RF_KEY_ALIAS` and `RF_KEY_PASSWORD` (Gradle properties or environment). It exists only when all four are set; when one to three are set the build fails with a `GradleException` naming the missing values; when none is set the release build type keeps the debug signing, so every existing workflow and local build is unchanged.
4. **Stable certificate for test builds**: `debug-release.yml` is the only writer. It restores `~/.android/debug.keystore` with `actions/cache/restore@v4` under the fixed key `repforge-debug-keystore-v1`; on a miss it creates the keystore with `keytool -genkeypair` (alias `androiddebugkey`, password `android`, `CN=Android Debug,O=Android,C=US`, 10000 days) and saves it at once with `actions/cache/save@v4`, before the build (a post-step save would only run if the whole job succeeded, so a later failure would lose the keystore). `android.yml` only restores (`actions/cache/restore@v4`) and never saves; on a miss it builds with a throwaway keystore and emits a warning. After the build, both workflows compare the SHA-256 that `keytool -list -v` reads from the keystore with the signer certificate SHA-256 that `apksigner verify --print-certs` reports for each built APK and fail on a mismatch, so the first run already proves AGP signed with the cached keystore. The certificate SHA-256 also stays in the existing "Verify APK signatures and metadata" output. No keystore is committed (standards section 9).
   Known limits, recorded rather than hidden: (a) the first run after this change creates a keystore that differs from every earlier build, so testers uninstall once (back up data first); (b) GitHub evicts cache entries unused for 7 days or over quota, which regenerates the certificate and needs one more uninstall; (c) an Actions cache entry is readable by runs on the branch that wrote it and on the default branch (and, for pull requests, the base branch); entries written on `main` by `debug-release.yml` are therefore visible to feature branches, but `debug-release.yml` also runs on the active campaign branch, which then writes its own entry; a branch that sees no entry builds with a throwaway keystore in `android.yml`, so its certificate differs from the rolling release; there is no write race because only the serial `debug-release.yml` saves; (d) the cache is not a secret store, and a debug identity with a public password is acceptable only because it signs test builds. A repository-secret keystore is the alternative and is an owner decision (see actions).
5. **NUT-023**, no schema change (see the section below).
6. **README**: a "Releases" paragraph and the test-build certificate note.

## NUT-023 — import source and date
Requirement (D04): (1) each imported food stores source name, source identifier and import date; (2) the source is visible in the food detail screen.

What is stored today (inspected, unchanged):
| Needed | Where it is stored | State |
|---|---|---|
| Source name | `foods.source`, `FoodSource` (`userCreated`, `openFoodFacts`, `seed`) | stored; Open Food Facts rows carry `openFoodFacts` |
| Source identifier | `foods.barcode`, and the food id `off:<code>` | stored for Open Food Facts: the mapper sets `barcode` to OFF's product `code` and the id to `off:<code>`. For these rows barcode and product code are the same value |
| Import date | `foods.created_at` | stored: the time the importer built the `Food` (`createdAt: now` in `open_food_facts_mapper.dart`). It becomes an import date only once the record is persisted: `LogFood` upserts an online food on first log (never rewriting `createdAt` afterwards) and `lookup_barcode.dart:88` upserts a scanned online hit at scan time. Caveat: that scan-path `upsert` rewrites `created_at` when a soft-deleted food is re-imported, so the date then is the re-import date, not the first one |

What this stage does: `foodSourceText` / `FoodSourceLine` (`app/lib/features/nutrition/presentation/food_source_line.dart`) show one caption under the food name in the portion sheet, the screen where a food's nutrition is seen before logging: "Source: Open Food Facts · <code> · imported YYYY-MM-DD" for imported foods that exist in the local database, "Source: Open Food Facts · <code> · not saved yet" for an online search hit that was never saved (the search screen opens the sheet with a freshly mapped food whose `createdAt` is only the mapping time, so no import date is claimed; the sheet checks `foods.byId`), "Your food · created YYYY-MM-DD" for user foods and "Source: built-in food list · added YYYY-MM-DD" for seed foods (none exist today). The date is the local calendar day of `createdAt`. NUT-023(2) is met for the portion sheet; widget tests cover imported, unsaved, user-created, seed and missing-code cases, a 320x640 layout with a long code and a UTC instant near midnight.

What cannot be done without a schema change, and is left as a remaining item:
- The source identifier is the `barcode` column reused. It is a true source identifier only for Open Food Facts; a future second source, or an Open Food Facts product that should be tracked by something other than its barcode, needs a dedicated `source_id` column. There is no per-food licence or attribution text, no source URL and no source data version either.
- `created_at` is the first local storage time, not a separately recorded "imported at": it is set when the record is first persisted (first log or scan), and the scan path rewrites it on re-import of a soft-deleted food (see the table). The earlier wording of this record, that an unsaved search hit displays the time of the search as its import date, described a defect of this stage's first version, not a schema limitation; it is fixed by the "not saved yet" caption. A later refresh of the product would need its own column (`updated_at` is rewritten by edits).
- The acceptance wording "stores source name, source identifier and import date" is therefore satisfied for Open Food Facts using existing columns, and not satisfied in the general form. Whether a dedicated column is worth a schema bump is an owner decision (schema work is held with WP 8's v8/v9 sequencing; this stage touched nothing under `app/lib/data/db/**` or `app/drift_schemas/**`).
- Only the portion sheet shows the line. The diary entry edit sheet and saved-meal and recipe screens show a logged snapshot, not the food record, and were not changed. There is no food-detail screen separate from the portion sheet.
