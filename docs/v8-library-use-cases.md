# Schema v8 library: blocked exercises at the domain, data and use-case layers (WP 8 sub-stage 3b-8)

- Status: **implemented in the isolated v8 zone, not connected to the app; awaiting review.** The owner's stage 3b decision baseline (D04 §7, 2026-11-06: unreadable data blocked individually, C-1, R-C4, R-C8) is implemented; awaiting independent review. Production stays on schema 7 (`AppDatabase`); no production repository, use case, provider or screen changed. Stage 3b stays unaccepted.
- Scope (D04 §7, 2026-11-06, "3b check scope"): blocked exercises cannot be selected for new work through the use cases; workout and session history stays readable; the report lists each blocked exercise with stable id and reason; the correction route leaves historical sessions unchanged. Screen checks move to 3d. ADR-0008 E Q14 (user attributes and overrides) and Q16 (custom copies copy values). R-01 (several reasons, resolved independently). No change to accepted WP 9 behaviour.
- Sources: D04 §7 (2026-11-06 entries); ADR-0008 (sections A to E); ADR-0009; `docs/schema-v8.md`; `docs/catalogue/equipment.md` §1; `docs/catalogue/quality-and-duplicates.md` §4.

## 2. Behaviour

| Availability | Selection and discovery | New work through a use case | By id and history |
|---|---|---|---|
| blocked (any unresolved block row) | never | refused, nothing written | read |
| archived | not offered (offered with `includeArchived`, as WP 9 history views) | refused for new entries; a saved plan keeps it (TD-42), exactly as WP 9 | read |
| retired | never | **not refused** (R-C8) | read |
| deleted | never | refused (not found) | read |

**Blocked reasons** (R-01, one row per reason): `noPrimaryTarget`, `unknownEquipment`, `invalidEquipment`, and since the decision baseline `invalidSecondaryTarget`, `invalidClassification`, `invalidAliases` (unreadable secondary muscles, type or category, alias list; `docs/schema-v8.md` section 7). An unreadable row is blocked by the migration; the guards also refuse an unreadable row without a block row (`availability: unreadable`) as a second line of defence.

**Correction route** (`correctBlockedReason`): the fix sets a whole field, and each fix resolves only its field's reasons:

| Field (`BlockedField`) | Fix | Resolves | Checked with |
|---|---|---|---|
| `targets` | `SetTargetsCorrection`: the target list (stored primaries first, then secondaries, ordinals contiguous from 0; a kept secondary can become the primary) | `noPrimaryTarget`, `invalidSecondaryTarget` | 3a rules on `targets` |
| `equipment` | `SetEquipmentCorrection`: the equipment list, may be empty (`equipment.md` §1 rule 2), so a legacy `"bodyweight"` or `"None"` is corrected faithfully | `unknownEquipment`, `invalidEquipment` | 3a rules on `equipment` |
| `classification` | `SetClassificationCorrection(type, category)`: both columns, domain identifiers by construction (`ExerciseType`, `ExerciseCategory`) | `invalidClassification` | domain values; the **WP 9 type rules** (C-10): a readable type never changes once sets are recorded or while a plan uses the exercise (WP 9 messages); an unreadable type may be set only to the type of every recorded set, and not while a plan uses the exercise; 3a rules on `type`/`category` when the result is readable |
| `aliases` | `SetAliasesCorrection(aliases)`: the en-GB alias list, stored as every WP 9 save stores it (trimmed, empty and duplicate aliases dropped), may be empty; `search_key` recomputed from name and aliases; the entry records the list given and the list stored | `invalidAliases` | the WP 9 save rules (C-9): an alias over 100 characters or more than 20 aliases refused |

Every active reason of the field is resolved (R-C4); a reason of another field keeps the exercise blocked (R-01). One transaction: the field's rows or columns, `resolved_at`, `updated_at`, one report run (trigger `userCorrection`) with one entry per resolved reason (action `corrected`, category `migrated`, rule of the resolved block, value before and after, R-06) and its counts (C-1). Plans, sessions, entries and sets are never touched; tests compare a digest of every row of those tables before and after.

**Notes (non-material, recorded):**
- N-1 v8 stores no equipment class (owner decision Q11). The reference data built for `validateExercise` gives every item the placeholder `EquipmentClass.other`; the rules never read the class, and this reference data is never returned.
- N-2 `selectable` does not apply the user's `hidden` flag (`exercise_user_state`); hiding is a discovery preference for 3d screens.
- N-3 `V8ExerciseReadPort` maps to WP 9 by name (19 muscle ids, 21 equipment ids, plan §4, IC-804, IC-806); an exercise with more than one primary or a target or item outside the WP 9 taxonomy is not representable and reads as null, as v7's mapper does for what it cannot read.
- N-4 The port's write side (`upsert`, `archive`, `delete`) is not part of 3b and throws; its streams emit one snapshot. Live watching and writes are 3d work.
- N-5 The isolated zone now includes `lib/data/repositories/v8/` (`schema_v8_isolation_test.dart`, `library_domain_isolation_test.dart`).
- N-6 `SetClassificationCorrection` sets both `type` and `category` (the whole classification), also when only one was unreadable. Its type follows the WP 9 type rules exactly (review DB H1): a set's type equals its exercise's type (`validateSetForExercise`), and a readable type cannot change once sets are recorded or while a plan uses the exercise (`SaveCustomExercise`). History and plans count as WP 9 counts them (sessions and plans that are not deleted). An unreadable type may be set only to the type of every recorded set; when the recorded sets have several types (v7 legacy data, for example `ex-long` in the frozen v7 fixture), no type matches and the classification cannot be corrected here. That follows from the WP 9 rule; it is not a new rule.
- N-7 The correction entry's `field` is the `BlockedField` name (`targets`, `equipment`, `classification`, `aliases`); `original_value` and `resulting_value` encode the field as JSON text (classification as `{"type":…,"category":…}`, aliases as the stored `aliases_json` text).

### C-11 (owner-visible limitation, re-check R1, 2026-11-06)
- **Case:** an exercise whose type cannot be read and whose recorded sets have several types, or a type outside the domain.
- **Effect:** no type can be set, so the user cannot correct it. The exercise stays blocked; its history stays readable.
- **Cause:** WP 9's set-type rule combined with "never rewrite history".
- **Evidence:** the frozen v7 data holds mixed-type sets (`ex-long`). No real exercise with an unreadable type and recorded sets is expected.
- **Status:** raised with C-10 for the owner. Behaviour is unchanged for now.
